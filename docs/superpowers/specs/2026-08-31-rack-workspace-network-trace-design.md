# 机柜工作区与线路追踪设计

## 目标

让日常工作从单个机柜和设备开始；从设备的精确端口进入物理线缆追踪。避免默认在一个页面绘制整机房的全部机柜和设备。

## 用户确认的范围

1. 日常使用以查找、管理某一个机柜内设备为主。
2. 每个设备详情页必须可查看该设备所有已登记端口。
3. 支持两种追踪：已知起点和目标时查看中间交换机；只知道起点端口时发现可到达终点。
4. 发现模式默认四跳、用户可扩展到十跳、单次最多显示一百个终点。

## 信息结构

机房级或机柜级 -> 选定机柜 -> 机柜工作区（现有 RackDeviceView） -> 设备详情 -> 端口与连接（现有全部端口表） -> 线路追踪（新页面）。

机柜工作区是默认设备操作入口。现有全机房设备拓扑保留为显式进入的“全景线路图”，不作为查设备或查端口的默认入口。

## 线路追踪规则

- 所有结果是已登记的物理线缆关系，不代表实时流量、VLAN、路由协议或真实数据包路径。
- 追踪从 `sourcePortId` 开始；不能以整台设备替代起点端口。
- 只有识别为网络设备的中间节点可以继续穿越；沿用现有设备类型关键词，不新增数据库字段或设备分类体系。
- 路径不得重复经过同一设备；按跳数和稳定 ID 排序。
- 无路径、达到跳数上限或结果被截断时必须说明原因。

### 已知目标模式

- 输入：起点端口和目标设备。
- 输出：一条确定的最短物理路径，包含设备名、设备类型、机柜号、两端端口和线缆类型。
- 最多十跳；不搜索备用路径；目标不可达时返回可显示的“无路径”结果。

### 发现终点模式

- 输入：起点端口、最大跳数（默认 4、范围 1–10）和固定展示上限 100。
- 输出：经网络设备可达的非网络设备端口；每项显示设备、端口、机柜和最短跳数。
- API 返回发现总数、实际返回数和截断标志。选择一个终点后，按已知目标模式展示该条路径。

## 前端呈现

- 端口与连接表每一行增加“线路追踪”；未连接端口显示不可追踪原因。链接携带 `sourcePortId` 和 `sourceServerId`。
- 追踪页使用现有 `GET /api/servers/{sourceServerId}` 与 `GET /api/servers/{sourceServerId}/ports` 校验该端口归属后，固定显示起点设备/端口和“已登记物理连接，非实时数据”。校验失败时不执行追踪请求。
- 页面提供“已知目标”和“发现终点”两个模式。已知目标通过现有设备名称搜索选择目标设备，不要求用户输入技术 ID。右侧只显示当前选中的一条路径和逐跳端口列表，不加载无关机柜或全机房设备面板。
- 每个节点可跳转设备详情，并保留返回追踪上下文。

## API 契约

保留 `GET /api/network-path?sourceId=&targetId=` 不变，新增：

1. `GET /api/network-path/by-port?sourcePortId={guid}&targetServerId={guid}`，返回 `pathFound`、`warning`、`reason`、`devices`、`hops`。
2. `GET /api/network-path/reachable?sourcePortId={guid}&maxHops={1..10}&limit=100`，返回 `warning`、`maxHops`、`totalEndpointCount`、`returnedEndpointCount`、`isTruncated`、`endpoints`。

参数无效返回 400；不存在的起点端口或目标设备返回 404；两条接口均为认证后的只读接口。

## 非目标

- 不新增数据库表、字段、迁移或第三方依赖。
- 不实现实时流量、VLAN、IP 路由、路由协议、自动发现或备用路径枚举。
- 不重写全景拓扑、CableLayer、线缆数据模型或现有端口维护。

## 验收标准

1. 机柜级选定机柜后进入单机柜工作区；全机房设备图不是默认设备入口。
2. 单设备详情仍显示全部端口及直连信息；每个已连接端口可进入线路追踪。
3. 已知目标时，结果从所选端口开始，返回一条不超过十跳的最短已登记物理路径。
4. 发现模式默认四跳、允许 1–10 跳、最多渲染一百个终点，并显示总数与截断状态。
5. 现有只读和修改权限、端口维护行为保持不变。
6. 后端集成测试、前端 Vitest、TypeScript、生产构建和 `git diff --check` 通过。
