# 设备经交换机连接路径示意方案（待 Claude 综合审核）

> 文档状态：方案建议，尚未形成产品需求基线或开发任务  
> 编写日期：2026-08-04  
> 目的：供 Claude 从产品范围、技术架构和实施优先级角度综合审核、补充与裁决  
> 注意：本文不授权修改 API、数据模型、前端页面或引入第三方依赖。

## 1. 需求背景

用户希望在当前机房空间、机柜和设备落位管理系统中，能够查看两台设备之间经过交换机的连接路线示意，例如：

```text
设备 A → 同机柜交换机 → 设备 B
```

设备可能位于同一机柜，也可能位于不同机柜。用户关注的是快速理解设备间如何连接、经过哪些交换机和端口，以便进行日常查询和故障排查。

## 2. 对真实业务目标的理解

### 2.1 实际使用者

- 机房运维人员
- 网络管理员
- 设备资产管理员

### 2.2 典型使用场景

1. 选择设备 A 和设备 B，查看两者是否存在已登记的连接路径。
2. 查看设备 A 接入了哪个交换机端口。
3. 查看路径经过哪些交换机、端口、线缆和机柜。
4. 在故障排查时确认系统登记的连接关系是否完整。
5. 跨机柜时，在机房平面图中快速定位涉及的机柜。

### 2.3 用户最终应看到的效果

路径详情以清晰的步骤展示：

```text
服务器 A（A01 机柜）
  eth0
   │ 铜缆 / CABLE-001
   ▼
交换机 SW-01（A01 机柜）
  GE0/0/1 → GE0/0/12
   │ 铜缆 / CABLE-002
   ▼
服务器 B（A01 机柜）
  eth0
```

跨机柜时，机房 2D 平面图同时高亮涉及的机柜和机柜间连接：

```text
A01 机柜 ───── B03 机柜
```

## 3. 必须明确的产品边界

建议第一阶段将功能命名为“连接路径示意”或“已登记连接路径”，不要称为“真实网络流量路线”。

现有系统记录的是设备端口和物理线缆，但没有以下运行态网络信息：

- VLAN 配置
- MAC 地址表
- IP 路由表
- 生成树状态
- 链路聚合关系
- ECMP 或其他多路径策略
- 交换机端口实时启停状态

因此，第一阶段可以回答：

> 按系统中登记的端口和线缆关系，两台设备经过哪些交换机连接。

第一阶段不能保证回答：

> 某个数据包在当前时刻实际从哪个交换机端口转发。

这是数据能力边界，不是单纯更换绘图库就能解决的问题。NetBox 社区也明确区分物理线缆追踪和交换机内部的二层转发路径；其物理追踪不会自动推导 VLAN 或交换机内部转发路线。

参考：https://github.com/netbox-community/netbox/discussions/10629

## 4. 当前项目基础与缺口

### 4.1 已具备的能力

当前项目已经具备：

- `Port`：设备端口模型。
- `Cable`：端口到端口的物理线缆模型。
- 端口和线缆管理 API。
- 线缆管理页面。
- 基于 Konva 的机房 2D 平面图。
- 不同机柜之间的线缆聚合和连线显示。
- 设备类型字段，可用于识别交换机。

相关现有文件：

- `src/backend/Datacenter.Api/Models/Port.cs`
- `src/backend/Datacenter.Api/Models/Cable.cs`
- `src/backend/Datacenter.Api/Models/Server.cs`
- `src/backend/Datacenter.Api/Controllers/CablesController.cs`
- `src/frontend/src/components/FloorplanCanvas.vue`
- `src/frontend/src/views/FloorplanView.vue`
- `src/frontend/src/views/CableListView.vue`

### 4.2 当前缺口

1. 系统能查询单条线缆，但不能计算设备 A 到设备 B 的多段路径。
2. 当前平面图按机柜绘制，不具备机柜内部设备级空间坐标。
3. 同一机柜内的设备和交换机在平面图上会落在同一个机柜节点，直接连线无法表达清楚。
4. 当前后端的机房线缆接口只返回跨机柜连接，并按机柜对聚合，不返回同机柜内部设备路径。
5. 当前系统没有交换机内部 VLAN 或真实转发数据，只能生成连接拓扑示意。

## 5. 推荐的 MVP 方案

建议采用“机房平面图高亮 + 路径详情侧栏”的组合，而不是试图把同机柜所有端口都画在机房平面图上。

### 5.1 用户交互

1. 用户从设备详情页或机房平面图点击“查看连接路径”。
2. 当前设备作为起点，用户选择目标设备。
3. 系统请求后端计算路径。
4. 找到路径后：
   - 右侧抽屉按顺序展示设备、端口、线缆、交换机和机柜。
   - 机房平面图高亮路径经过的机柜。
   - 跨机柜路径高亮机柜间连线。
5. 找不到路径时，明确显示“未找到已登记的连接路径”，并提示检查端口或线缆登记。
6. 页面固定提示：“本结果为已登记连接拓扑示意，不代表实时数据包路由。”

### 5.2 为什么使用侧栏展示同机柜路径

机房平面图表达的是机柜的真实位置，而不是机柜内部每台设备、每个端口的水平位置。同机柜中的服务器与交换机在平面图上共用一个机柜坐标，如果强行画线，线段会重叠或缩成一个点。

侧栏能够清楚表达：

- 设备顺序
- 输入、输出端口
- 线缆类型
- 线缆标识
- 所在机柜
- 异常或缺失连接

它也不会破坏项目“2D 平面图为主、单机柜局部展示为辅”的既有架构约束。

### 5.3 后端路径计算

第一版建议不新增数据库表，直接使用现有设备、端口、线缆和设备位置数据生成临时图结构：

- 节点：设备。
- 边：一条端口到端口的线缆。
- 边属性：两端端口、线缆 ID、线缆类型、颜色、长度。
- 起点和终点：用户选择的两台设备。
- 中间节点：仅允许设备类型明确为“交换机”的设备。
- 路径选择：使用广度优先搜索（BFS），返回经过设备数量最少的路径。

示例：

```text
服务器 A — SW-01 — SW-02 — 服务器 B
```

禁止普通服务器作为中转节点，避免因为错误登记产生以下误导路径：

```text
服务器 A — 普通服务器 C — 服务器 B
```

## 6. 路径规则建议

第一阶段建议采用以下明确规则：

1. 起点和终点不能相同。
2. 只读取状态有效且仍存在的设备、端口和线缆。
3. 中间设备必须是交换机。
4. 线缆方向不代表网络方向，路径搜索按双向连接处理。
5. 多条可用路径并存时，第一版只返回跳数最少的一条。
6. 相同跳数存在多条路径时，必须使用稳定排序，保证重复查询结果一致。
7. 路径设置合理的最大跳数或访问节点上限，避免异常数据造成过度搜索。
8. 任一端设备未上架时，可以返回路径，但必须明确显示“设备未上架/无机柜位置”；是否允许由 Claude 裁决。
9. 路径中的设备或端口信息缺失时，不静默伪造结果。

## 7. 建议验收标准

### AC-01：同机柜单交换机路径

已登记“设备 A → 交换机 → 设备 B”的两条线缆后，选择 A 和 B，应展示两段线缆、交换机及四个实际端口；平面图高亮所在机柜。

### AC-02：跨机柜路径

设备位于不同机柜且存在交换机连接路径时，应在详情侧栏展示完整设备顺序，并在机房平面图高亮经过的机柜和跨机柜连接。

### AC-03：无路径

两台设备之间没有已登记路径时，应显示“未找到已登记的连接路径”，不得画出推测路线。

### AC-04：禁止普通设备中转

如果唯一的图路径需要经过一台普通服务器，系统应判定无有效路径，不得把普通服务器当作交换机转发节点。

### AC-05：多条路径的稳定结果

存在多条路径时，第一版返回最少跳数路径；相同数据重复查询应返回相同结果。

### AC-06：展示边界提示

所有路径结果必须显示“已登记连接拓扑示意，不代表实时数据包路由”。

### AC-07：权限

拥有机房和设备只读权限的用户可以查看路径；路径查询不修改任何业务数据，不要求修改权限。

### AC-08：现有功能不回归

现有设备、端口、线缆管理和机房平面图编辑功能继续正常工作。

## 8. 明确不进入第一阶段的内容

- 自动登录交换机读取配置。
- SNMP、LLDP 或厂商 API 自动发现。
- VLAN、MAC 地址表和路由表建模。
- 实时数据包转发路径计算。
- 实时流量、带宽或故障动画。
- 链路聚合、生成树和 ECMP 多路径分析。
- 全机房高精度线缆走线动画。
- 新增独立图数据库。
- 替换现有 Konva 平面图。
- 为未来需求提前建立通用拓扑插件框架。

## 9. 开源项目与技术参考

### 9.1 NetBox Topology Views（首选业务与交互参考）

- GitHub：https://github.com/netbox-community/netbox-topology-views
- 适合参考：设备节点、线缆边、物理/逻辑连接区分、邻居过滤、路径高亮、坐标保存、设备角色图标。
- 不建议直接集成：它依赖完整 NetBox/Python/Django 体系，直接引入会产生第二套资产数据、权限、部署和同步机制。

建议借鉴其交互与表达方式，不复制或嵌入整套系统。

### 9.2 NetBox

- GitHub：https://github.com/netbox-community/netbox
- 适合参考：设备接口、线缆终端、配线架以及物理连接追踪的数据语义。
- 重要边界：物理线缆追踪不等同于交换机内部 VLAN 或真实转发路径。

### 9.3 Cytoscape.js（未来独立拓扑页候选）

- GitHub：https://github.com/cytoscape/cytoscape.js
- 优点：支持图可视化、路径算法、节点选择、高亮和多种自动布局。
- 当前判断：如果未来需要独立的“全网拓扑页面”且节点规模明显扩大，可以重新评估；第一版没有必要引入。

### 9.4 vis-network（简单自动布局拓扑候选）

- GitHub：https://github.com/visjs/vis-network
- 优点：Canvas 渲染、自动布局、聚类、图标和交互成熟。
- 当前判断：适合独立自动布局网络图，不适合替换当前带真实机柜坐标的平面图。

### 9.5 openDCIM（DCIM 业务参考）

- GitHub：https://github.com/opendcim/openDCIM
- 适合参考：交换机端口和设备连接管理。
- 当前判断：可作为业务模型参考，但不建议作为当前 Vue 前端的实现基础。

## 10. 技术方案取舍

| 方案 | 优点 | 问题 | 当前建议 |
|---|---|---|---|
| 复用 Konva + 后端路径接口 | 改动小、无新依赖、与现有平面图一致 | 需要自行实现路径侧栏和高亮 | 推荐作为 MVP |
| 引入 Cytoscape.js | 图算法和拓扑交互强 | 新增依赖、形成第二套画布 | 未来独立拓扑页再评估 |
| 引入 vis-network | 自动布局成熟、上手快 | 与真实机柜坐标场景不完全一致 | 暂不引入 |
| 部署并集成 NetBox | 数据模型成熟、生态完整 | 双系统、同步、权限和部署成本高 | 不推荐当前采用 |
| 立即采集交换机实时配置 | 可接近真实转发路径 | 厂商差异、安全凭据、网络访问和维护成本高 | 明确延后 |

## 11. 建议的最小实施拆分

如果 Claude 批准产品范围，再由 Architect 按权威工作流建立正式任务。建议最多拆为两个实施任务，避免过度治理：

1. 后端：路径查询契约、最短路径计算、权限和测试。
2. 前端：设备选择、路径侧栏、机柜/连线高亮和测试。

不建议把数据结构、算法、API、每个组件分别拆成大量独立任务。

## 12. 需要 Claude 综合审核和裁决的问题

1. 产品名称是否确定为“连接路径示意”或“已登记连接路径”？
2. 是否确认第一阶段只表示登记拓扑，不承诺真实数据包路线？
3. 入口放在设备详情页、机房平面图，还是两处都提供？建议两处都可进入，但复用同一个侧栏组件。
4. 目标设备选择范围是当前机房、全系统，还是当前机柜？建议默认当前机房，并允许按名称搜索。
5. 未上架设备是否允许参与路径查询？建议允许查询连接关系，但明确标识“未上架”，且不在平面图定位。
6. 多路径第一版是否只展示一条最少跳数路径？建议是。
7. `DeviceType` 中交换机的标准值是否已经统一？如果存在“交换机、网络交换机、核心交换机”等多个自由文本值，需要先裁决识别规则；不建议通过模糊字符串长期判断。
8. 是否要求路径中显示线缆编号？当前 `Cable` 模型只有 ID、类型、颜色、长度和备注，没有面向用户的线缆编码字段。如果必须显示业务线缆编号，将涉及数据模型变更。
9. 是否需要支持配线架？当前模型只允许端口属于设备，尚无配线架实体。建议第一阶段不支持，避免扩大范围。
10. 是否需要展示路径不可用原因，例如具体指出哪个设备端口没有登记线缆？建议第一版只给出无路径提示，详细诊断延后。

## 13. 初步风险

### 13.1 交换机类型不规范

如果设备类型是任意文本，后端无法可靠判断哪些设备可以作为中间交换节点。正式设计前应检查现有数据和录入选项。

### 13.2 “最短路径”被误解为真实路由

BFS 得到的是已登记连接图中经过设备数量最少的路径，并非网络协议选择的路径。界面必须持续显示边界提示。

### 13.3 数据不完整导致无路径

路径计算依赖端口和线缆登记质量。如果实际已连接但系统未登记，结果只能显示无路径，不能自动猜测。

### 13.4 同机柜平面图表达能力有限

同机柜内部路径不适合直接画在机房平面图中，应以路径侧栏或单机柜局部视图为主要承载方式。

## 14. 当前推荐结论

建议批准一个不新增数据库表、不新增前端依赖的 MVP：

1. 复用现有设备、端口、线缆和机柜位置数据。
2. 后端计算只允许交换机作为中间节点的最少跳数连接路径。
3. 前端以路径详情侧栏展示端口级步骤。
4. 机房平面图只负责高亮机柜及跨机柜部分。
5. 明确标注该结果是登记拓扑示意，不代表实时数据包路由。
6. 将 VLAN、交换机发现、真实路由、多路径和实时动画全部延后。

该方案能够以最小改动形成可运行、可验证的完整闭环，也为以后是否增加逻辑网络模型保留了清晰边界。
