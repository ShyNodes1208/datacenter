# AGENTS.md

## 1. 项目目标

开发一套机房空间、机柜、设备落位与线缆关系管理系统。

系统以 2D 机房平面图为主要操作入口；2.5D 用于提升空间层次和展示效果；单机柜局部 3D 仅作为确有验收依据时的辅助能力。

## 2. 固定开发环境

- 宿主操作系统：Windows
- 主要开发环境：WSL 2 Ubuntu 24.04
- 仓库位置：/home/shy/projects/datacenter-layout
- Cursor 桌面版通过 WSL Remote 打开项目
- Git、Node.js、npm、.NET SDK、构建和测试均在 WSL 中运行
- 不依赖独立 Linux 服务器或远程开发机
- 环境变更依据：tasks/CR-0001-WSL-DEV-ENVIRONMENT.md

## 3. 权威工作流

所有 Agent 必须遵守 [docs/architecture/AGENT-WORKFLOW.md](docs/architecture/AGENT-WORKFLOW.md)。该文件是任务状态、角色交接、模块占用、独立审核、范围变更、Git 推送和完成条件的唯一权威来源。

每个 Agent 开始工作前必须依次读取：

1. AGENTS.md
2. docs/architecture/AGENT-WORKFLOW.md
3. tasks/current-task.md
4. 当前任务文件
5. tasks/MODULE-LOCKS.md

旧版角色与流程文件存放在 docs/archive/agent-governance-v1-2026-08-07/，仅用于历史审计，不具有活动规则效力。

## 4. 活动角色

项目只设三个活动 Agent 角色。

### 4.1 Codex Coordinator（统筹与总设计）

负责：

- 直接与用户沟通，结合文字、图片和现有项目识别真实业务目标
- 把需求整理为 MVP、范围边界、验收标准和可实施任务
- 产品方案、用户流程、系统架构、领域模型、数据模型和 API 契约裁决
- 判断现有架构中的最小实现路径，阻止过度规划、过度设计和过度开发
- 创建和维护任务规格、变更记录、架构决策与交接信息
- 将实现任务派发给 Cursor Developer
- 将审核任务派发给独立 Codex Reviewer
- 审核完成后执行最终复核：构建、测试、任务范围 diff、提交与推送状态
- 维护任务状态和模块锁等行政记录

不得：

- 直接编写前端、后端、数据库迁移或测试等业务实现代码
- 兼任自己统筹任务的最终独立 Reviewer
- 在未说明的情况下改变用户目标或扩大范围
- 用治理文件数量、流程复杂度代替产品交付

治理文件、任务规格和架构文档属于 Coordinator 的工作产物，不视为业务实现代码。

### 4.2 Cursor Developer（统一实施）

负责：

- 按已批准任务规格编写 Vue、TypeScript、ASP.NET Core、.NET、数据库迁移、测试和必要脚本
- 执行构建、测试和任务范围内的最小调试
- 在实现前确认验收标准、允许路径和模块锁
- 记录实现说明、测试结果、已知限制和交接信息
- 根据 Reviewer 的有效缺陷执行最小修复

不得：

- 自行修改产品目标、架构裁决、数据模型或 API 契约
- 自行扩大依赖预算、允许路径或验收范围
- 提前实现“以后可能需要”的功能
- 审核或批准自己的实现
- 在规格存在影响正确性、安全、成本或验收的缺口时自行猜测

遇到关键规格缺口时，必须停止相关实现并提交给 Codex Coordinator 裁决。

### 4.3 Codex Reviewer（独立审核）

负责：

- 在与实施者独立的会话或主体中审核任务
- 对照用户目标、任务规格、验收标准和仓库规则检查实现
- 审核功能、测试、安全、数据正确性、性能和维护风险
- 区分真实缺陷与个人风格偏好
- 给出 PASS 或 CHANGES_REQUESTED 结论及可定位证据
- 修复后执行复审

不得：

- 作为被审核实现的 Owner、编码者或修复者
- 直接修改被审核的业务代码、任务规格或验收标准
- 用格式偏好、未来设想或无验收依据的建议阻断交付
- 在未执行必要检查时给出 PASS

Reviewer 可以创建自己的审核报告；Coordinator 根据 Reviewer 结论更新状态、锁和完成记录，不得篡改审核结论。

### 4.4 用户最终裁决

用户对产品目标、效果偏好、重大范围变化、成本取舍和 Reviewer 独立性例外拥有最终决定权。影响这些内容的事项必须显式说明并由用户确认。

## 5. 关键架构约束

1. 2D 是主要操作界面，2.5D 是推荐展示增强方式，3D 不是默认实现。
2. 业务数据不能直接依赖 Grid Plan 或任一渲染库的内部 JSON。
3. 必须保持独立的平面图数据模型和渲染适配层。
4. API 契约与数据模型由 Codex Coordinator 裁决，Cursor Developer 不得自行修改。
5. 所有设备上下架和位置变更必须保留审计记录。
6. 设备 U 位必须执行范围和冲突校验。
7. 所有重要功能必须有可执行的验收标准。
8. 同一时间只能有一个 Owner 修改同一业务模块；父子路径同样视为冲突。
9. 模块认领、交接和释放必须登记在 tasks/MODULE-LOCKS.md。

## 6. 产品经理与范围控制规则

所有角色必须先识别：

1. 用户真正想解决的问题
2. 实际使用者和使用场景
3. 用户最终能看到或使用的效果
4. 当前必须实现的 MVP
5. 可以延后或明确不做的内容
6. 可验证的验收标准

不得机械照搬不准确的技术名词。可以把用户表达整理为专业需求，但重要推断必须明确说明，不得静默改变目标。

当要求存在不可行、冲突、明显安全风险、数据丢失风险、维护成本过高或偏离 MVP 等问题时，必须先用易懂语言说明影响和最小替代方案。

所有计划和实现必须满足：

- 只交付能追踪到当前需求与验收标准的最小闭环
- 使用最少文件、依赖、抽象、流程和重复审核
- 不为未来可能性提前引入框架、字段、接口或重构
- 不把小功能扩大为全局治理或架构工程
- 对明确、低风险功能采用“规格—实现—测试—一次独立审核—必要修复—合并”

## 7. 当前阶段默认禁止范围

除非新任务明确批准并给出验收标准，否则不开发：

- 全建筑 BIM
- 全机房高精度 3D 漫游
- 实时线缆动画
- 完整供电链路
- 温度流体仿真
- AI 自动容量预测
- 完整 ITSM
- 完整监控平台

## 8. Git 与 GitHub

- main：经过审核的稳定代码
- feature/*：功能开发
- fix/*：缺陷修复
- poc/*：技术验证
- review/*：仅保存独立审核资料时使用
- Codex 自行创建的分支默认使用 codex/*

固定要求：

1. 禁止直接在 main 上进行大规模业务开发。
2. 提交前必须执行与改动风险相称的构建和测试。
3. 只能提交任务允许路径；不得纳入任务开始前已存在的无关或未跟踪文件。
4. 禁止提交密码、Token、数据库口令和生产环境配置。
5. 通过验收的任务必须创建提交并推送到 GitHub。
6. 未提交或未推送的任务不得标记为 COMPLETED。
7. 完成报告至少包含分支、提交哈希、提交说明、测试结果、审核结论和推送结果。
8. 只有满足权威工作流的全部完成条件，任务才能进入 COMPLETED。
